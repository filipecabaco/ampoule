1. What ampoule is and what it is used for

ampoule turns a Mix project into one executable file per platform. The file carries your release unchanged, the BEAM compiled to WebAssembly and precompiled to native code, and an operating-system layer written in Rust. Copy it to a Mac or a Linux machine and run it: nothing else has to be installed there.

$ cd my_app
$ ampoule release
==> MIX_ENV=prod mix release --overwrite
==> my_app 0.1.0: 1018 files, 11.6 MiB → 5.2 MiB image (32 paths pruned)
_build/prod/ampoule/my_app-aarch64-darwin (26.3 MiB)
==> packed in 0.3s; run `<binary> help` for its commands

$ _build/prod/ampoule/my_app-aarch64-darwin start
[info] Running MyApp with Bandit 1.11.1 at 0.0.0.0:4000 (http)

The file behaves like the release's own bin/my_app: start, eval, your own commands such as migrate, configuration from environment variables, and a clean init:stop() on SIGTERM.

2. What you need to know before you use ampoule

Do not use ampoule if your app

  • starts host programs: ports, :os.cmd/1 and System.cmd/3 cannot start anything;
  • needs Erlang distribution: the app runs as one node;
  • is built with an OTP major other than 28: the engine runs ERTS 16.

Take special care

  • NIFs are rebuilt for wasm when you pack, from C, C++ or Rust. Packing them needs wasi-sdk 34, and Rust NIFs also need rustup target add wasm32-wasip1-threads.
  • A thread a NIF starts must return from its function. enif_thread_exit ends it without cleanup, and joining that thread never returns.

What packing needs

Elixir and Erlang/OTP 28 on the machine that packs. The machine that runs the file needs nothing.

3. How to use ampoule

Run it in your project's root. It runs mix release and packs the result.

$ ampoule release

Then run the file the way you would run the release's script:

$ ./my_app-aarch64-darwin start
$ ./my_app-aarch64-darwin eval 'IO.puts(MyApp.version())'
$ PORT=8080 ./my_app-aarch64-darwin serve

If your app migrates a database before it starts

Put the order in ampoule.toml at the project root; packing stores it in the file.

serve = ["migrate", "start"]

[commands]
migrate = "MyApp.Release.migrate()"

[start.env]
PHX_SERVER = "true"

serve then runs the migrations and starts the app; migrate runs them on their own.

Packing for other platforms

One machine packs for all four targets. Put each target's ampoule-<target> binary from a release in a directory:

$ AMPOULE_STUBS=~/ampoule-stubs ampoule release --target aarch64-darwin --target x86_64-linux

4. Possible side effects

What changes when an app runs under ampoule instead of its own release script:

  • The app reports itself as Linux on every host: :os.type() returns {:unix, :linux}.
  • Each run gets a private /tmp, removed when the app exits. A run that wrote erl_crash.dump keeps it and prints where.
  • Precompressed static files (.gz, .br) are not packed; Plug.Static serves the uncompressed file.
  • .beam files lose their debug and docs chunks, so Code.fetch_docs/1 has nothing to show.

5. How to run and store ampoule

On a server, copy the file and run it:

$ scp my_app-x86_64-linux server:
$ ssh server 'DATABASE_URL=… ./my_app-x86_64-linux serve'

In a container, the file is the only thing the image needs:

FROM scratch
COPY my_app-aarch64-linux /my_app
ENTRYPOINT ["/my_app"]
CMD ["start"]

Stop it with SIGTERM or Ctrl-C: the release shuts down through init:stop() and exits 0, as it would natively. A second signal, or an app still running after --stop-timeout, exits at once.

The app sees only its mounts: the release at /app, a private /tmp, /etc/hosts, /etc/resolv.conf, the host's CA bundle, /dev/null, a generated /proc, and anything you pass with --mount. Symlinks resolve inside that view, never the host's. --listen, --port-map, --deny-connect and --rewrite-connect decide which ports it binds and where it may connect.
